# 解剖层字段规范

只有在报告明确讲清目标“如何设计”时，才算完成解剖层。读者应能沿总图逐层追问，并找到对应答案，而不必自行猜测层与层之间怎样衔接。

## 先总图，再逐层，再走一次完整请求

1. **真实结构总图**：标明输入与入口、执行者、主要模块、外部依赖、结果和实际执行终点；有统一调度程序则指向源码，没有则说明谁在组织调用。
2. **业务全链路图**：适用于含多种业务技能的集合。用泳道或分层子图展开主要阶段，箭头注明交接的材料；标注这是文档要求的协作、代码调用，还是报告作者的组织建议。不能把业务分类画成不存在的自动系统。
3. **逐层说明**：节点用稳定编号链接到下表。跨层连接至少能回答“上层的什么产物，成为下层的什么输入”。

| 层/节点 | 进入时拿到什么 | 内部具体动作 | 为什么这样设计 | 判断/失败时怎么办 | 输出什么、交给谁 | 证据 |
|---|---|---|---|---|---|---|

4. **端到端展开**：选与用户问题最相关的实际入口，画全主路径及影响行为的分支。多模式技能分别展开各模式：例如创建/优化、有无外部输入、脚本成功/失败。逐步追踪同一份材料的变化，而不是再列一遍模块清单。
5. **细节覆盖**：主要层全部解释；次要模块可放完整索引/展开卡。对未读正文或无法证实的模块明确注明，不能仅凭名字声称完成源码分析。

判断节点标明条件和出口；源码没有规定停止条件就写“未规定”，作者建议的缺数停止不能画成原逻辑。一个大仓不必把所有细节挤进单图：总览负责完整关系，子图负责细节。

## 可读性与证据

- 图中的英文标识保留准确拼写，并紧跟中文解释；CLI、ASIN 等首次出现要解释。
- 第一屏或目录后即出现完整总图，逐项验货必须在解剖层后。
- 架构事实、设计意图和适配建议分开标注。避免把示例数字、硬编码旧参数或期望输出当成真实工具返回。
- 图、说明表、CLI 表共用事实底稿，检查节点有无孤立、分支去向有无遗漏、Markdown 和 HTML 是否一致。
- 视觉验收须查看真实渲染：文字不遮挡、箭头去向清楚、桌面可读、手机无整页横向溢出。按 `fresh-report-style.md` 的标准档执行，不自动扩展为所有图逐一截图。Markdown 中保留可编辑图源。
- 默认复用随包 HTML 模板；主要层全部展开，次要接口与证据可用 `details` 收纳，不得隐藏主链。总图复杂时用总览加分支子图，或模板的纵向节点组件；节点之间标交接产物，分支写条件与去向。没有真实关系时不得为了适应模板硬连线。

## 代码仓 / 有脚本的 Skill

必须依次说明：

1. **输入形式**：GitHub URL、本地路径、配置、文件或参数；
2. **入口**：`main`、命令、Web 路由、配置加载点；
3. **CLI/API 表**：每一条真实入口的命令/签名、参数、默认值、输入输出和副作用；
4. **中间产物**：扫描 JSON、缓存、数据库、生成文件等如何被下一阶段消费；
5. **模块关系**：谁调用谁、数据怎么走；
6. **判断与回退**：条件、失败时发生什么、什么时候中止；
7. **依赖与限制**：第三方库、网络、模型、文件大小、权限；
8. **证据**：每一项附真实 `路径:行号`。

## 纯 Markdown Skill

它没有真实 CLI/API。不要造一个。将接口表改成：

| 触发语/入口 | 需要的输入 | 内部判断 | 输出 | 边界 |
|---|---|---|---|---|

同时解释它对 Agent 的提示词协议：何时触发、强制步骤、不能做什么、产物放在哪里。

## 呈现准则

- 先讲输入和入口，再讲处理中间过程，最后讲输出与限制；
- 用“用户执行命令后发生什么”解释 CLI，而不是只贴命令；
- 模块表不是文件列表：每项至少解释职责、关键子流程和上下游；
- `路径:行号` 是核验入口，正文仍要用白话。
